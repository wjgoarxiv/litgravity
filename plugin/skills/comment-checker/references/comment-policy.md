# Comment policy and the added-comment scan

Open this reference when a post-edit sweep or an audit needs the detailed rules: the decision order, what each classification means, the comment markers per language, the cases that only look like comments, the directive comments that must survive, and the receipt format. The decision about what to keep stays with the model and the repository's own rules.

## Decision order

1. Identify the edited file and the exact new or changed comment lines. Unrelated pre-existing comments stay out of the review unless the user put them in scope.
2. Read the smallest surrounding unit that establishes intent: the function, type, branch or configuration entry. A comment cannot be judged without the code it describes.
3. Classify the comment as `retain`, `rewrite`, `remove` or `needs-context`.
4. Apply the smallest correction and rerun the narrow verification for the edited surface.
5. Report which scan state applies (`warning`, `clean`, `not-run`, `error`, `not-applicable`). Silence, a refused command and a clean verdict are three different outcomes.

## Classification

**Retain** a comment when it carries information the code cannot express economically:

- the reason for a non-obvious constraint or ordering requirement;
- an external contract, specification, issue or compatibility boundary;
- a security, privacy, data-loss or recovery invariant;
- units, coordinate systems, tolerances or assumptions needed to interpret an algorithm;
- a deliberate exception to a repository convention;
- a bounded follow-up with an owner or tracking reference.

**Rewrite** a comment when the underlying reason is useful and the wording is stale, vague, too broad or disconnected from the current symbol. The new text explains the decision and its consequence, and leaves line-by-line narration behind.

**Remove** a comment that repeats a name or operation, paraphrases syntax, marks an obvious section, preserves deleted code, narrates the edit just made, or promises something unsupported. Before removal, use repository search or history to confirm the comment is no marker consumed by tooling, documentation generation, coverage control, a formatter or a test.

**Needs-context** applies when the comment refers to an external contract that is unavailable, the code looks intentionally surprising, or removal could change generated documentation or operational procedures. Ask for the smallest missing fact.

## Comment markers by language

The scan filters added diff lines with these markers. Pick the row for the file's extension.

| Family | Extensions | Line marker | Block marker | Doc comment |
|---|---|---|---|---|
| C-like | `.c .h .cpp .cc .hpp .java .kt .swift .cs .go .rs .js .jsx .ts .tsx .mjs .cjs .php .scala .dart` | `//` | `/* ... */` | `///`, `/** ... */`, `//!` |
| Shell and config | `.sh .bash .zsh .py .rb .pl .yaml .yml .toml .r .ex .exs .tf` | `#` | none (Python uses string literals; Ruby `=begin`) | Python docstring `"""`, Ruby `##` |
| SQL and Lua | `.sql .lua .hs .elm` | `--` | `/* */` (SQL), `--[[ ]]` (Lua), `{- -}` (Haskell) | `---` |
| Lisp family | `.el .lisp .clj .scm` | `;` | `#\| \|#` | docstring |
| TeX and MATLAB | `.tex .m` | `%` | `%{ %}` | none |
| Markup | `.html .xml .svg .vue .svelte` | none | `<!-- -->` | none |
| Stylesheets | `.css .scss .less` | `//` (scss, less) | `/* */` | none |

Unknown extension: read ten lines of the file and infer the marker, or report the file as outside the scan.

## Lines that look like comments and are not

- A shebang (`#!/usr/bin/env node`) on line 1.
- `#include`, `#define`, `#pragma` and other preprocessor lines.
- `#` inside a string, a regex, a URL fragment (`https://host/path#anchor`) or a CSS id selector.
- Markdown headings inside a docs file that happens to use `#`.
- Python string literals used as data rather than docstrings.
- `//` inside a URL in a string (`"https://example.invalid"`).
- Template literals and heredoc bodies, which hold text that merely contains marker characters.

A hit is confirmed by reading the line with its neighbors in `read_file`; the filter only nominates candidates.

## Directive comments that survive

Treat these as code. Removing one changes tooling behavior.

| Family | Examples |
|---|---|
| Lint suppression | `eslint-disable`, `eslint-disable-next-line`, `# noqa`, `# pylint: disable=`, `// nolint`, `#[allow(...)]`, `// biome-ignore`, `# rubocop:disable`, `// @ts-ignore`, `// @ts-expect-error`, `# type: ignore`, `# pyright: ignore` |
| Formatter control | `// prettier-ignore`, `# fmt: off`, `# fmt: on`, `#[rustfmt::skip]`, `// clang-format off` |
| Coverage | `/* istanbul ignore next */`, `/* c8 ignore next */`, `# pragma: no cover`, `// coverage:ignore` |
| Code generation | `//go:generate`, `// Code generated ... DO NOT EDIT.`, `# generated by`, `// @generated` |
| Build and platform | `//go:build`, `// +build`, `#region`, `#endregion`, `// swiftlint:disable`, `#if` guards written as comments |
| Licensing | `SPDX-License-Identifier:`, `Copyright (c)`, `@license`, `/*! ... */` banners that minifiers keep |
| Shell | `# shellcheck disable=SC####`, `# shellcheck source=` |
| Editors and modelines | `# -*- coding: utf-8 -*-`, `# vim: set ...`, `// swift-format-ignore` |

A directive without a reason gets the reason added (`// eslint-disable-next-line no-await-in-loop -- order matters: each call reads the previous write`). A directive whose removal leaves lint, types and tests clean is a candidate for removal, confirmed by running the gate.

## Doc comments

Doc comments on public API feed generated documentation and editor hovers. They keep their format (JSDoc tags, rustdoc sections, Go doc sentences starting with the symbol name, Python docstring conventions) even when they restate part of the signature. Review them for truth: renamed parameters, removed arguments, changed units, changed error behavior. A doc comment that lost its subject after a refactor is FIX: misleading.

## Findings are data

A scan hit does not prove a defect. For a false positive, retain the comment and give the specific reason in the receipt. When the same false positive recurs, propose a change to the scan filter separately and leave the product comments as they are.

## Verification receipt

Name the file and changed comment, the classification, the scan state, the exact targeted command used to verify behavior, and any unresolved context. For ordinary source edits, the relevant unit, type, lint or docs check is the decisive proof; comment prose alone is no proof. Keep the final report narrow:

```text
Comment: path and line or symbol
Decision: retained | rewritten | removed | needs-context
Reason: repository-specific intent
Scan: warning | clean | not-run | error | not-applicable
Verification: exact command and result
```

## Worked sweep

A change adds a retry loop to `src/client.js`. The diff shows three added comment lines:

```text
src/client.js:41: // Now we retry the request
src/client.js:44: // upstream 503s during deploys, so retry 3x (#412)
src/client.js:52: // TODO fix this
```

Line 41 is narration (REMOVE: narration). Line 44 states the reason and carries a ticket (KEEP: intent). Line 52 is a bare marker (FIX: vague): it becomes `// TODO(ops): drop the retry once the deploy gate lands (#431)` when the user supplies the owner and ticket, and moves to `questions.md` when nobody can supply them. The receipt lists one removal, one keep and one open question; the scan state is `warning`; the gate is `node --test` on the client tests, run after the edit, and `git diff --word-diff` shows only comment tokens changed.

## Reader-facing wording

State counts and the corrected misleading comments first, then open questions, then the gate result. The inventory file keeps the per-comment table for readers who want it.
