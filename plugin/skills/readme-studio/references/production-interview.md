# Bounded README production interview

The model reads this reference with `read_file` from the skill folder when a material choice is open, then puts the question to the user with `ask_question`, attaching a recommended default to each question. In a headless run nobody can answer, so choose the least invasive default for the open axis and append it as a `decision` line in `.litgravity/ledger/<conversation-id>.jsonl`. No interview is mandatory. Ask when two plausible answers would materially change scope, architecture, permissions, accessibility or visual direction. README examples include a conflict over audience or purpose, incompatible content scope, a static versus motion delivery that alters accessibility or package contents, and an unresolved authorized output location.

Suppose the brief calls both directions acceptable yet neither picks one nor hands the pick to you. That direction stays unresolved, because agreement that either works selects nothing. Apply this rule to each material axis the brief leaves open. Ask one high-impact question at a time, starting with the most consequential choice, and give each remaining material choice its own round after the higher-impact answers arrive. Run as many rounds as the work materially needs, with no fixed question count. Hold back any announced default and any affected work until the user answers. A default is allowed once the brief has settled that axis, explicitly delegates it (for example "your call" or "pick one"), or the alternatives would leave the result unchanged.

When the material questions have answers, state the default and proceed on details that are settled, delegated or immaterial to the result. Lean on repository facts, applicable instructions, established identity and earlier answers for those details, and go ahead with ordinary reversible work without a ceremonial approval step. Keep unrelated questions in separate rounds.

Carry earlier answers across rounds in the conversation and the task-local direction note. On resume, reread the confirmed choices and inspect partial work before asking anything new, and keep resolved questions closed. An answer narrows the current task and carries no wider file, host, permission, credential, network or publication authority. Review, plan and keyword-only requests remain read-only.

Those read-only requests stay read-only whatever the interview reveals: production questions never convert them into a README edit, asset generation or package change. After a cancellation, stop new writes and record the partial status; on resumption, reuse the confirmed facts and assets.
