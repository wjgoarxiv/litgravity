# Safe change playbook

This reference expands the `refactor` entry point for transformations whose risk crosses several files, runtime boundaries, generated artifacts, public APIs or persistent data. Read it in full before the plan is written, then keep it open while steps execute: the sections answer the questions that come up when a step goes red.

## Decision packet

Write a compact packet before the first edit and store it at the top of `.litgravity/evidence/<slug>/codemap.md`:

```text
Target:
Structural outcome:
Observable behavior preserved:
Explicit non-goals:
Consumers:
Baseline commands:
Real scenario:
Migration order:
Rollback:
```

Each line is a sentence or a command, and every line comes from repository evidence. A packet with a blank line means the refactor is not ready: go back to analysis, or ask the user the one question that fills the line. "Consumers" lists in-repo importers, external packages, scripts, docs and configuration that read the target. "Real scenario" names one end-to-end run (a CLI invocation, an HTTP request, a built-package import) that is cheap enough to repeat after every slice.

## Dependency map

Build a directional map, with the arrow meaning "depends on":

```text
input boundary
  -> parser or adapter
    -> domain owner
      -> side-effect port
        -> external system
```

Put package exports, generated inputs, configuration, persistence, user documentation and tests beside the node they constrain. Mark cycles and import-time side effects. A list of files is an inventory; direction is what makes it a dependency map.

For each proposed move, answer these five questions in the codemap:

- Who owns the invariant after the move?
- Which layer may depend on which?
- What public surface remains?
- What construction or initialization order changes?
- Which error and cancellation path crosses the new seam?

An answer of "unchanged" needs a pointer to the line that proves it. An answer of "unknown" turns into a characterization test or an experiment before the step starts.

## Compatibility strategies

Pick one strategy per public surface and write it into the plan.

### Atomic internal change

Use when every consumer sits inside one repository and can migrate in one checked patch. Keep the diff coherent, run the full gates and verify the built or packaged form, because a source-level pass leaves runtime module resolution untested.

### Add, migrate, remove

Use when consumers migrate in stages:

1. add the new surface;
2. delegate from the old surface to the new one without changing behavior;
3. migrate the known consumers;
4. show the old surface has no remaining in-scope use (a scoped search plus the checker CLI);
5. remove it once compatibility authority allows.

The shim between steps 2 and 5 has an owner, a warning when the old surface is called, a removal criterion and a date. An untracked "temporary" alias becomes permanent by default.

### Dual read or dual write

Use for persistent-data migrations with an explicit consistency rule. Define which representation is authoritative, how divergence is detected, the deploy order, the backfill, the rollback and the moment the dual path ends. Dual writes without reconciliation create two sources of truth, so the plan includes the reconciliation job and its stop condition.

### Versioned boundary

Use when external consumers cannot migrate together. Keep the old version, add the new contract beside it, and define support and removal criteria. A breaking change carries its own label and its own approval; the word "refactor" does not cover it.

## Generated artifacts

Classify each generated file before touching anything near it:

- **authoritative output**: always regenerated, edited only through its source;
- **checked-in output**: regenerated by a named command and reviewed as a diff;
- **template or input**: the source of truth, edited directly;
- **cache or build product**: ignored by version control and removable.

Find the generator and its deterministic invocation before editing checked-in output. When regeneration changes unrelated regions, stop and explain the drift. Accepting a noisy generated diff hides the real change from reviewers and from the equivalence check.

## Error preservation

Refactoring changes errors by accident more often than it changes results. Compare at the outward boundary:

- error type or code;
- cause chain;
- message contract when users read it;
- exit status or HTTP status;
- retryability;
- partial side effects before the failure;
- logging ownership (who logs, and how many times);
- cancellation versus failure.

Internal exception classes are part of the contract only when a caller observes them. A failure-path scenario (invalid input, missing file, dependency down) run before and after is the cheapest proof.

## Ordering and side effects

Extraction and movement can shift:

- evaluation order and short-circuiting;
- lazy versus eager work;
- lock acquisition;
- transaction boundaries;
- initialization timing and import-time effects;
- event emission order;
- resource lifetime and cleanup;
- retry scope.

For high-risk paths, write the event or state sequence before and after the move and compare the two. Equal final values leave intermediate effects open, and intermediate effects are what downstream consumers often rely on.

## Performance preservation

When speed, memory or throughput belongs to the contract, capture comparable before and after evidence:

- the same build mode and runtime version;
- the same dataset and warmup;
- a distribution of runs, with one timing kept out of the claim;
- allocation or resource counts when they matter;
- a correctness check on the benchmark output.

A faster result bought by skipping validation, cancellation, durability or cleanup is a regression and gets reported as one.

## Data and schema migrations

A schema or persisted-format change is a public migration. The plan lists every reader and writer, every stored version in the wild, the order in which deployments reach them, and the recovery path when a writer ships before its readers. Prefer an additive change followed by a later removal over an in-place rewrite. Keep a fixture of the old format in the tests until the removal lands, so the compatibility claim stays executable.

## Choosing between mechanical and structural editing

- A rename of one symbol with complete references: the compiler-assisted tool or a structural rewrite with a dry run.
- An argument reorder across many files: structural rewrite with a manifest, then the checker CLI on every touched package.
- An extraction: hand edits in a single step with characterization tests around the seam.
- A module split: one responsibility per slice, with the public path kept as a re-export until the last slice.
- A dependency replacement: wrap the old dependency behind an adapter first, switch the adapter second, delete the old dependency last.

## Failure response

At the first unexplained regression:

1. stop later slices;
2. preserve the failing command and its output;
3. identify the earliest slice that introduced it;
4. revert or correct only that owned slice;
5. rerun the baseline and the failing scenario;
6. update the plan before resuming.

Piling fixes onto an unbounded broken state costs more than the revert. Recovery uses `git restore -- <your files>` on files you own; stash, reset and clean stay out because the working tree may hold the user's edits.
